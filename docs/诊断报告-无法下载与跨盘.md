## 0. 结论摘要（三句话）

1. **用户「无法下载」的直接原因 = A（选错账号）**：用户 23:26–23:27 的三次（实为四次）目录下载都在「百度网盘（2）」实例的 `/IDA95` 下，该目录实测 `dir_empty=1`（0 文件/0 目录），新代码正确地拒绝建任务并提示「目录为空…请确认所选账号/路径是否正确」；同路径在主账号「百度网盘」下有 **10 文件 / 5 目录**，用主账号 CLI/GUI 下载均成功。
2. **但确实存在一个真实功能回归 B（高权重，可 100% 复现）**：HEAD `3979d96` 把「目录下载/目录跨盘」从「1 个递归任务、引擎内部串行」改成「预扫描后每文件一个任务、默认最多 16 个并发」。对**光鸭云盘作源**时，3 个并发任务就会触发服务端 `服务端错误(127)：操作过于频繁`；重试 3 次仍以同样并发猛冲，**3/3 任务全失败**（跨盘两次独立复现）；把 `small_file_concurrency` 降为 1 后同一操作 **3/3 全部成功**。这直接构成「无法跨网盘传输 / 批量下载失败」。
3. **C（预检缺失）存在**：跨盘「写只读目标」没有前置 `write_ok` 检查。目录跨盘在「扫描阶段」因目标 `ensure_dir` 失败而中止（能拦住，但报错文案误报成「扫描目录失败」）；**单文件**跨盘则完全没有预检，会先完整下载源文件、再在目标上传时失败（白下载）。此外用户主账号百度当前 `write_ok=false`（空间超限：used 9.94TB > total 2.21TB），任何「写入百度主账号」都注定失败。

### B. 真实功能回归：批量任务并发突发 + 重试不降并发，把光鸭云盘的限流变成全军覆没（权重：高，解释「无法跨盘传输」）

复现（详细见 §2 #8/#9，命令见 §6）：

- 默认配置（`transfer.small_file_concurrency = 16`，见 `crates/wp-core/src/config.rs:76`）下，从光鸭目录跨盘 3 个文件到夸克：
  - 23:41 跑一次：`3/3` 任务 `失败：服务端错误(127)：操作过于频繁，请稍后重试（已重试 3 次）`（`/tmp/diag/g2.out`、`/tmp/diag/data_g2/任务.json`）

- 对照实验：只把 `transfer.small_file_concurrency` 改成 **1**，其余不变同一操作 → **3/3 全部成功**，夸克侧文件 1024/2048/11 B 齐全（`/tmp/diag/g2c.out`；`wp-cli --drive quark ls '/_diag_quark_dst3/_diag_cross'`）。
- 同类现象也出现在「光鸭目录下载」：默认并发 3 个文件首次全 127，重试 2 轮后才成功（`/tmp/diag/g1.out`）——下载链路本身是通的，但批量/跨盘稳态会失败。
- 机制（源码级）：
  - HEAD `crates/wp-gui/src/app.rs:1404 enqueue_download_entries` / `:1472 enqueue_cross_copy` 现在把目录**逐文件建任务**（`:1420-1461` 预扫描 → `Event::DirPlanReady`，`:1840-1911` 逐文件 `enqueue_*`）；
  - 引擎按 `small_file_concurrency`（默认 16，`crates/wp-transfer/src/control.rs:172`）**并发启动**这些小文件任务；本实验 3 个文件即 3 并发。

  - 即：**回归由 `3979d96` 的“预扫描 + 逐文件任务展开”引入**（本意是修「目录下载假完成」，副作用是并发突发），光鸭云盘 API 对突发请求限流（业务码 127），重试又保持同一并发再次突发，最终全部失败。
- 判定：**B 成立**。影响面：光鸭云盘作**源**的目录下载、目录跨盘、多选文件下载/跨盘（一次 ≥3 个文件时高概率触发）。夸克/百度源尚未测到同等强度限流（见 §5 未测项）。

## 4. 最小修复建议（指到文件:行，均为 HEAD `3979d96` 行号）

> 注意：工作区已有未提交的同类修复（`crates/wp-gui/src/app.rs`、`dialogs.rs`、`crates/wp-transfer/src/lib.rs`、新增 `crates/wp-transfer/src/plan.rs`，截至 23:51 未落库/未验证）。以下建议用于核对/补齐，不重复造轮子。

### 4.1（对应 B，最高优先级）限流防护：按「源网盘」串行或限 QPS，重试要退避而非同时再冲

- 位置：`crates/wp-transfer/src/control.rs:172-173`（`Gate::new(cfg.small_file_concurrency/large_file_concurrency)`）
- 最小改法（任选其一，1 处改动即可显著缓解）：
  1. 给 `Gate` 增加**按 drive_id 维度**的并发上限（如每实例同时最多 1–2 个请求），默认 `small_file_concurrency` 对同一网盘实例生效（光鸭/夸克/百度各 1），不同网盘之间仍可并行；
  2. 或把默认 `small_file_concurrency` 从 16 降到 2–3（`crates/wp-core/src/config.rs:76`），并在设置页提示「过大易被网盘限流」；
  3. 重试退避加**抖动 + 指数增长**（当前 `crates/wp-transfer/src/engine.rs:2225 backoff_ms`：1.5s/3s/6s 固定基数；3 次重试窗口约 10.5 s，小于光鸭限流窗口，且同一秒所有任务一起重试又会形成第二次突发）。建议对 127/429 类错误单独设更长退避（≥30 s）并串行重试。
